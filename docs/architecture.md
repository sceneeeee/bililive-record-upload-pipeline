# 架构与状态边界

录播姬独立录制到宿主 video/，对应容器 `/rec`；API 同时映射为 `/app/video`。Webhook 通知开关分段，API 后处理完成后异步调度上传。上传主体、重试设置、分 P/合并和定时扫描继续使用上游实现。

`upload-streams-and-path.patch` 关闭原始及限速读取流，并将 filePath、fileSize、dev/ino/size 写入任务 extra。`immediate-upload.patch` 用 WeakMap 保存每个 live 的运行 Promise 与待办类型 Set，按请求类型串行处理；handled/raw/未指定类型均保留，异常释放锁，等待周期扫描补充，不无限自动重试。不同直播可并行。

清理器将闭合分段、完整源路径、上传父子任务与五项 stat 身份关联。历史任务没有路径时，还需完整任务名/标题、唯一候选、相等字节数与关闭/任务时间顺序。拒绝越界、symlink、硬链接和身份变化。

删除必须同时满足：上传及父任务终态、关联兄弟任务终态、对应 handled/raw 回调结束、无录制或活动任务引用、所有可扫描进程均无对应开放 inode。最终失败仅在显式开启时有资格；手动取消保留，父任务最终失败引起的子取消仅在失败删除开启时有资格。API 重启后使用持久记录，失踪的活动任务或未结束回调不能变成成功证据。原始 API 不提供可靠的全量持久队列，本清理器也不恢复上传队列。

删除前重新获取 API，重新核对身份与 FD，持久化 delete_intent，再复核并通过目录 FD、NOFOLLOW、unlink、目录 fsync 删除；错误按 2–60 秒退避并持久记录。不存在的文件记录 absent、释放量为 0。对应任务归档后才移除终态 UI 记录。

上游 `afterUploadDeletAction=delete` 的原生成功删除仍然保留，其保护范围由上游决定。旁路清理器的检查不能追溯撤销上游已经执行的删除。video/ 必须只允许受信任的录播和上传进程写入；stat/FD 检查与 unlink 并非跨进程原子操作，不能作为恶意并发写入者的隔离机制。

清理器以 root 扫描 `/proc`，只在完整扫描时删除；运行在容器或 hidepid 等限制下须先验证可见性，不能屏蔽 PermissionError。台账与应用数据库分开，状态目录0700、台账0600。系统服务设置 UMask0077、低调度优先级和内存限制。监控只读查询业务，写自身状态/journal，不自动重启、补传或删除。
