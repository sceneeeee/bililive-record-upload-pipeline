# 生产证据与版本对应关系

本文记录历史部署与当前公开版本之间已知的关系。内容经过匿名化，不包含服务器地址、主机路径、账号、房间、稿件标识、原始日志、数据库记录或凭据。

## 结论摘要

历史部署已实际运行录播与自动投稿工作流，并有自然 FLV 分段、Webhook/后处理、文件上传终态和父投稿/编辑操作的聚合证据。但历史生产实例并未运行当前公开仓库的完整实现。

**因此，历史生产观察证明的是项目的历史祖先工作流曾真实使用，不是当前公开 commit 的完整生产认证。**

## 版本对应矩阵

| 项目 | 历史生产观察 | 当前公开仓库 | 结论 |
| --- | --- | --- | --- |
| BililiveRecorder 镜像 | 锁定 digest 匹配 | 2.18.0 digest 锁定 | 匹配 |
| biliLive-tools API / Web 镜像 | 实际镜像 digest 匹配 | 3.20.0 digest 锁定 | 当前观察时匹配；API/Web 部署引用仍使用 tag，重建可复现性弱于 digest 引用 |
| 上传流与文件身份补丁 | 运行 bundle SHA256 匹配 | 同一输出 SHA256 | 有对应证据 |
| 即时上传调度补丁 | 历史 bundle 使用旧 dirty-flag 实现 | 当前 bundle 使用按类型保存的 pending Set | 不同 |
| 清理器 | 使用历史独立服务/脚本 | 使用本仓库 pipeline 命名的公开实现 | 不同 |
| 录播监控 | 使用历史独立服务/脚本 | 提供新的公开 systemd units | 不同 |
| API 维护窗口 timer | 历史实现未启用 | 公开实现为可选功能 | 不应作为业务故障判据 |

## 调度差异

历史调度实现使用运行 Promise 与 dirty 标志。并发请求到达时只记录“需要再运行”，下一轮仍可能复用第一次调用的请求类型。

当前公开实现使用每个直播独立的待办类型集合，分别保留 `handled`、`raw` 和未指定类型的请求，并在完成后释放运行状态。离线 Node.js 回归测试通过；历史生产基线在对应的合成并发反例中未通过。

这说明公开版本修复了一个可由离线测试复现的请求类型保留问题。它**不能证明**历史生产实际漏传了多少文件，也不能代替当前公开版本的自然直播验证。

## 清理策略差异

历史生产清理器是独立的 `sv-*` 服务和脚本，允许将最终失败的父/子任务作为删除候选。历史台账中确有最终失败源文件被删除的记录。

当前公开清理器的默认策略是最终失败保留；只有显式提供 `--delete-final-failure` 才允许失败终态进入后续删除资格判断。即使启用该选项，文件身份、父子任务、回调、FD 和 API 完整性检查仍然必须通过。

不要将历史生产清理行为描述为当前公开清理器的生产验证。迁移时必须显式核对旧策略、保留需求和存储容量，不能自动继承历史失败删除行为。

## 可公开引用的历史观察

匿名化历史审计支持以下有限陈述：

- 历史部署实际运行过 FLV 分段录制、Webhook/后处理和上传工作流。
- 历史台账中存在文件上传和父投稿/编辑操作的成功及失败终态。
- 多次成功的父投稿/编辑操作关联到相同的稿件标识，支持曾发生续传或合并类工作流。
- 历史部署经历过磁盘空间压力、上传失败和日志读取/解码异常，因此不能描述为整个观察期无故障。
- 日志轮转和损坏限制了部分历史窗口的可观测性；无法可靠计算完整的重试次数、恢复率或公开视频分 P 顺序。

这些是聚合的历史观察，不是 SLA、独立视频成功率或对当前公开代码的认证。公开投稿页面未能通过匿名公开接口完成核验，因此不在此声称具体公开视频数量、时长或 P 数。

## 发布与迁移原则

1. GitHub Release 只发布公开源码和说明，不部署到生产服务器。
2. 公开默认失败保留策略不得被历史生产配置静默覆盖。
3. 生产调度旧实现与公开新实现的差异必须保留在版本说明中。
4. 上游镜像、补丁输入/输出 SHA256 和第三方许可证必须在每次发布时重新校验。
5. 新清理器、监控、重启恢复、取消保留和维护窗口需要在独立环境验证。
6. 未经单独审批，不得通过 Release、CI 或仓库脚本连接生产主机、重启服务或删除录像。
